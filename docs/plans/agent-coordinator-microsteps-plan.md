# Agent 架构微步骤实施计划

依据：[《查找 Agent 架构规划》](codex://threads/01a1c889-e4c7-7fb3-8a9d-688ccadb4dce) 中用户确认的主链，以及[社区架构记录](../voice-agent-community-architecture-research.md)中的职责划分。

```text
用户 ⇄ 语音主 Agent ⇄ 唯一持久协调 Agent ⇄ 独立任务 Agent × N
           ↓                   ↓
        即时小工具       分派、跟进、汇总、观察、长期目标
```

每次实施一个编号，完成后验证并提交。一个编号只增加一种行为；若实际落地时同时牵动两种行为，就在该编号下面继续拆 checkbox。下文共 56 个可执行小步，checkbox 表示实施进度。

默认按编号顺序执行，每步使用前面已经完成的能力；跨轮依赖在正文注明。每轮结束都有一个能演示的成果，可以在该处停下来体验，再开始下一轮。

## 实现边界和复杂度取舍

1. **协调会话使用独立的 Pi Agent。** 它持有连续消息，只注册分派、查询、更新任务等协调工具。它不占 Worker（任务执行者）的并发名额；否则两个 Worker 运行时，协调者可能没有名额处理用户改口。模型解析、消息存档和追踪复用现有代码。
2. **协调会话串行接收事件，Worker 可以并行。** 同一协调会话每次只执行一轮，期间到达的用户消息和完成事件排队。这个小队列归协调会话所有，成本是一份待处理事件列表；用途是避免两个模型轮次同时修改同一上下文。
3. **任务执行仍由现有 `PiAgentExecutor`／`PiTaskRunner` 负责。** 手机宿主提供按 ID 的任务操作。协调模型决定怎么分派，代码负责启动、保存和回传。
4. **有状态对象使用类，工具注册和摘要整理使用普通函数。** 协调会话需要统一拥有消息、事件队列与关闭行为；纯数据转换没有独立生命周期，直接用函数。
5. **新增代码按两种生命周期集中。** 协调会话放在 `packages/looi-runtime/src/agent/core/coordinator-session.ts`；手机任务接线放在 `apps/nsh/runtime/agent-tasks.ts`。前者隐藏模型轮次和排队，后者隐藏任务启动、工具绑定及结果回调。文件名为预定位置，实施时可按实际接口调整。

代表调用关系：语音工具把用户要求交给协调会话；协调会话调用 `startTask(prompt)` 得到任务 ID，结束本轮；任务完成后代码把结果送回同一协调会话，再由它形成语音回传。语音继续复用现有 `run_agent_task`、`manage_agent_task` 名称，由桥接层转交协调会话。

这条链复用当前手机内 NSH＋Pi、SQLite 和语音协议适配器。新增成本集中在一个持久协调上下文、一个串行事件队列，以及每个任务与协调会话的关联数据。

## 第 1 轮：先接上协调 Agent（01—09）

这一轮的成果：只跑一个 Worker，但任务已经真正经过协调 Agent 分派和汇总。

- [ ] **01：提供独立于前台输入框的单任务启动入口。**
  - 从 `MobileRuntime.run()` 提取任务启动到 `agent-tasks.ts`，旧前台入口调用它。
  - 返回稳定的任务 ID 和完成 Promise；第一步仍只允许一个 Worker。旧前台入口保留其 UI 操作检查，内部派发沿用当前任务设置。
  - 完成标准：同一条任务从旧前台入口和新内部入口执行，都能在现有任务页查到结果。
- [ ] **02：实现只有对话能力的协调会话。** 复用 Pi 模型解析和当前模型配置，增加 `CoordinatorSession`，持有自己的消息和串行输入队列。完成标准：连续输入“我下午出发”“我什么时候出发”，第二轮能利用第一轮信息；此步先验证进程内连续性。
- [ ] **03：把语音提交入口改接协调会话。** 由 `MobileRuntime` 创建协调会话，修改 `VoiceTaskBridge` 的受理语义及 `run_agent_task` 接线，同步 NSH 的运行时构建导出。完成标准：语音请求进入协调会话，不再直接调用 Worker；保留短等待窗口，超过窗口返回“已受理”，不等待整项工作。
- [ ] **04：让协调会话的普通回答回到语音。** 复用快路径工具回执和 `enqueueNotice()`。完成标准：窗口内完成的回答直接随工具返回；超时的回答在空闲时播报，同一次回答只走一条路径。
- [ ] **05：给协调 Agent 增加“启动一个任务”工具。** 调用 01 的入口，立即返回任务 ID，随后结束协调轮次。完成标准：“研究一个问题”会启动 Worker，协调 Agent 不等待它执行完；用户可以继续说话。
- [ ] **06：让 Worker 结束事件回到协调会话。** 将完成、失败和取消结果作为协调输入，由协调 Agent 汇总，再复用 04 回到语音。完成标准：Worker 的原始结果只交给协调 Agent，语音听到的是协调后的汇报。此步更新 `docs/arch/index.html` 及其配套架构数据，反映新增主链。
- [ ] **07：查询通过协调 Agent。** 将 `VoiceTaskBridge.inspect()` 的同步读取改为异步协调受理，`manage_agent_task` 复用 03—04 的短等待与回传。完成标准：“进度怎么样”由协调 Agent 查询并回答，较慢查询不会一直占住语音工具调用。
- [ ] **08：停止通过协调 Agent。** 增加协调侧取消工具，先作用于唯一活动任务。完成标准：“先停下来”经过协调 Agent 停止刚才的任务，语音侧只接一个 Agent。
- [ ] **09：在开发真机横屏验收第一条闭环。** 依次验证提交任务、继续闲聊、查询进度、空闲汇报及取消；记录实际问题。完成标准：01—08 的链路使用真实语音和当前模型工作。

## 第 2 轮：让协调者跨语音连接和 App 重启延续（10—14）

- [ ] **10：给协调会话固定身份并保存消息。** 协调 Session ID 独立于前台文字会话和语音 WebSocket，复用 `SessionTranscriptStore`；每轮结束保存。完成标准：关闭再启动 App 后，协调 Agent 仍记得上一轮的出发约束。
- [ ] **11：保存协调会话与任务的关联。** 在现有 SQLite 存储中补充关联记录，任务详情仍来自现有任务表。完成标准：重启后协调 Agent 可以查询先前任务的状态与结果；执行中断状态沿用已有恢复语义。
- [ ] **12：补齐语音重连时的协调接线。** 重新建立 LIVE 时连接原协调会话；语音结束只解除语音接线。完成标准：结束 LIVE 再唤醒，协调会话和任务关联仍在；App 关闭时协调模块结束当前调用并保存记录。
- [ ] **13：接好模型切换。** 沿用现有模型切换入口，关闭旧协调模型调用，再用同一协调记录创建新实例。完成标准：切模型后仍能跟进原任务。
- [ ] **14：明确前台“新对话”的作用。** 该操作创建前台文字 Session，协调 Session 保持连续。完成标准：前台新对话后仍可询问协调 Agent 原来的任务。开发真机横屏验收重连、重启、切模型与新对话。

## 第 3 轮：把一个 Worker 扩成两个（15—25）

- [ ] **15：每个新任务分配独立 Session。** 协调 Session、前台文字 Session、各 Worker Session 分开，任务续接才复用原 Worker Session。完成标准：先后运行 A、B，A 的工具历史不会出现在 B 的输入上下文。
- [ ] **16：工具逐任务绑定任务 ID。** 调整工具构造入口，将家居、底座等工具绑定到所属任务，替换全局 `getActiveTaskId()`。完成标准：注入两个受控 Runner，分别执行工具，步骤和操作记录归属各自任务；真机并发留到 25。
- [ ] **17：任务输出按任务保存、显示。** 任务页按选中 ID 读取 Shell 输出与步骤状态。完成标准：切换已运行的 A／B 可以查看各自内容。
- [ ] **18：交互问题按任务保存、回答。** Store 按任务 ID 保存待回答问题，沿用原交互 UI。完成标准：用受控 Runner 产生 A、B 两个问题，回答 A 只恢复 A。
- [ ] **19：提供按 ID 停止的手机入口。** 协调工具和任务页都调用它，现有全局停止操作保留其原用途。完成标准：受控 Runner 中停止 A，B 的执行和问题不受影响。
- [ ] **20：从任务集合计算活动状态。** 替换前台单个 `busy` 的执行含义，UI 读取活动任务集合。完成标准：受控任务 A 先结束、B 仍运行时，App 仍显示有任务执行。
- [ ] **21：配置与关闭入口使用任务集合。** 模型切换、服务配置和关闭时机沿用已有行为，改为读取 20 的活动状态；协调模型轮次也纳入对应生命周期判断。完成标准：存在活动 Worker 或协调轮次时，旧配置入口不会提前重建正在使用的模型实例。
- [ ] **22：把手机执行器容量设为两个。** 只调整 Worker 名额，协调会话使用其独立模型实例。完成标准：宿主定向验证可启动两个独立 Session，第三个仍返回容量已满。
- [ ] **23：解除语音 Store 的单任务准入。** 派发入口从检查单个 `busy` 改为调用任务模块，由执行器管理名额。完成标准：语音先后提交 A、B 时两项均能运行，仍可向协调 Agent 查询。
- [ ] **24：让第三个任务进入等待队列。** 队列归手机任务模块，空出 Worker 名额后启动；查询和取消也能作用于排队项。完成标准：A、B、C 中 C 先排队，A 完成后 C 启动；取消排队的 C 则不会启动。
- [ ] **25：让协调 Agent 一次派出两项独立工作。** 使用前述能力处理“研究路线，同时整理购物清单”。完成标准：两项工作有独立 ID、各自结果都回到同一协调会话。开发真机横屏验收并更新架构图中的并发与任务归属。

## 第 4 轮：让用户能改口和续接（26—30）

- [ ] **26：给运行中的 Worker 增加追加要求入口。** 由 `PiAgentExecutor` 定位 Runner，使用 Pi 的 `steer()`（执行中追加指令），使新要求在当前工具调用结束后的模型步骤可见。完成标准：运行中的路线任务收到“改成下午出发”，继续使用原任务和原 Session。
- [ ] **27：给已结束的 Worker 增加续接入口。** 新建一次执行记录，复用原 Worker Session，并记录前后关联。完成标准：“在刚才方案上再加公交选项”能够读取原方案，历史任务结果仍可查询。
- [ ] **28：给协调 Agent 注册更新／续接工具。** 工具接收任务 ID 与新要求，代码按运行状态调用 26 或 27。完成标准：协调 Agent 可以通过工具改变现有工作，无需重建一项无关任务。
- [ ] **29：把语音里的补充要求交给协调 Agent 定位。** `manage_agent_task` 增加更新操作和消息正文；协调 Agent 从任务目标与近期对话选择相关任务，需要区分时提出具体问题。完成标准：“路线改成下午，购物清单照旧”只更新路线任务。
- [ ] **30：把 Worker 的问题交回协调 Agent。** 沿用已有交互记录，由协调 Agent 将需要的信息交给语音或现有任务页；语音回答经协调层投递给对应 Worker，审批交互继续使用原界面。完成标准：A 询问出发地点时，用户回答后只恢复 A。开发真机横屏验收改口、续接与回答问题。

## 第 5 轮：结果回传能保留多项事实（31—36）

- [ ] **31：用多任务摘要替代单份最新回执。** 语音上下文包含当前目标、活动任务与已完成结果摘要，任务详细输出仍按 ID 查询。完成标准：B 完成后，语音仍能回答 A 已完成的内容；摘要组装由代码完成。
- [ ] **32：保存待表达的协调结果。** 在现有 SQLite 中保存通知 ID、内容和待投递状态。完成标准：语音断开时 A、B 先后完成，重启后仍能读出两条待表达记录。
- [ ] **33：记录语音表达的实际进度。** 将已有发送、播放结束和打断事件关联到通知 ID。完成标准：可以区分待投递、已发送、完整播完和中途打断，完整播完的记录不再待投递。
- [ ] **34：重连时投递待表达记录。** 活跃会话继续复用空闲播报；待机期间留到下次对话。完成标准：语音重连后收到保留的结果，已播完的结果不重复加入；被打断的汇报按记录进度交给协调 Agent 决定后续表达。
- [ ] **35：让协调 Agent 区分背景更新与需要汇报的结果。** 输出包含背景摘要和可选表达内容，语音侧分别调用 `setContextNote()` 与通知入口。完成标准：普通步骤进度只更新背景；任务结束后生成一次简洁汇报，播报仍等待现有空闲窗口。
- [ ] **36：支持对已汇报结果继续追问。** 语音把“为什么选这条路线”交给协调会话，由它读取任务结果或续接 Worker。完成标准：追问能够使用详细结果；开发真机横屏验收用户说话期间完成任务、两项结果回流与断开重连。

## 第 6 轮：让同一个协调 Agent 开始观察和纠正（37—43）

- [ ] **37：输出最终用户话语事件。** 在语音协议归一化之后使用 `transcriptionFinal`，带已有话语标识；中间转写继续只服务 UI。完成标准：一句话的多次转写修订只形成一条最终用户事件。
- [ ] **38：输出带播放状态的助手回复事件。** 生成文本与完整播完分开，打断时复用 `playedPosition()` 记录已播位置，标明普通回复或协调通知的来源。完成标准：打断后的记录不把未播完的文本记为用户已听到。
- [ ] **39：把对话事件送入协调会话。** 以完成的一轮对话为单位排队，标明对话、委派、协调反馈的来源并关联原轮次／工具调用。完成标准：闲聊也能进入协调上下文；已委派内容只启动一份工作，协调反馈留在历史中但不再次触发同一观察。
- [ ] **40：加入协调上下文的滚动摘要。** 保留近期原文，较早对话整理成目标、约束和纠正；按模型可用上下文设置预算。完成标准：多轮后仍保留“下午出发”等有效约束，Worker 大段输出留在任务详情；摘要阈值集中在协调会话中。
- [ ] **41：给协调 Agent 增加观察输出。** 同一个协调会话在收到对话事件时判断是否有遗漏或矛盾；没有发现则结束本轮。完成标准：用户明确说过下午，语音随后说上午时，协调 Agent 能形成指向原话的纠正。
- [ ] **42：把观察反馈注入语音。** 普通背景纠正更新当前指令，需要告诉用户的纠正复用通知入口。完成标准：后续回答采用下午，反馈保留其来源和轮次关联。
- [ ] **43：让语音侧反过来纠正协调 Agent。** 用户改口或语音模型发现协调结论与已知对话不一致时，经同一协调入口回传纠正，再调整相关任务和摘要。完成标准：用户说“我又改回上午了”会替换旧约束；语音模型指出协调结果仍写下午时，协调 Agent 能修正原结论。开发真机横屏验收双向纠正，结合调用记录调整观察频率和摘要预算。

## 第 7 轮：长期目标用事件推进（44—51）

- [ ] **44：保存一个具体长期目标。** 首个场景采用“洗衣结束告诉我”，记录目标、设备、触发条件、当前状态与协调会话归属，放入现有 SQLite。完成标准：协调 Agent 可以新增、列出该目标，重启后仍能读取。
- [ ] **45：让家居状态采集独立于页面刷新。** `HomeRuntime` 当前只提供主动读取，在手机运行时增加由活动目标驱动的定期读取；与家居页面共用该次状态结果。完成标准：App 停在首屏，目标设备状态仍会更新。
- [ ] **46：提供目标设备的状态变化通知。** 比较 45 的前后快照，只在相关设备变化时通知目标模块。完成标准：相同状态反复读取不产生新变化，运行到结束产生一项变化。
- [ ] **47：把洗衣状态变化接给目标。** 命中运行到结束条件后唤起协调会话，再走 35 的表达路径。完成标准：受控状态变化能推进目标并形成一次提醒，模型在等待期间没有空转调用。
- [ ] **48：重启后恢复目标观察。** App 激活时恢复采集并读取当前设备状态，由协调 Agent 跟进仍在运行或已经结束的目标；待表达内容复用 32—34。完成标准：App 重开后可以继续跟进洗衣目标，完成后目标转为已完成。
- [ ] **49：支持取消长期目标。** 语音交给协调 Agent，由它停用目标及相应采集。完成标准：“别盯洗衣机了”会停止跟进；没有活动目标时不再为目标读取设备。
- [ ] **50：支持修改长期目标。** 沿用目标记录切换设备或条件，更新相关采集。完成标准：“改成看烘干机”后只有新设备变化能推进该目标。
- [ ] **51：开发真机横屏验收一个真实目标。** 使用真实设备验证创建、停留首屏等待、结束提醒、重开 App、修改与取消。需要按时间触发的目标在出现具体场景时，沿用该目标记录补调度字段。

## 第 8 轮：给语音补充简单命令（52—56）

52—54 可在 01 的宿主能力提取完成后提前实施；55 依赖 03—05 的协调入口，56 依赖 23—25 的并发链路。放在最后是为了先交付协调与多任务主链。

- [ ] **52：接通一个短命令 `date`。** 在现有手机 Shell 能力上暴露语音工具，首个操作只有获取当前时间，按手机时区返回实际命令结果。完成标准：“现在几点”通过工具返回，不启动协调模型或 Worker。
- [ ] **53：增加 `pwd`。** 在同一语音工具中增加查询工作目录操作。完成标准：工具返回手机执行环境的实际工作目录。
- [ ] **54：增加工作目录内的 `ls`。** 工具用明确操作和路径参数生成命令，复用现有执行与短等待机制。完成标准：语音可以列出工作目录内容；工具描述列出这三个已有操作，其他工作交给协调 Agent。新增成本是三个操作映射，用于先交付读取用途。
- [ ] **55：把即时工具与委派规则写入语音提示词。** 现有底座直接控制、上述三个命令由语音处理，多步工作交给协调会话。完成标准：混合请求中的即时操作走工具，多步任务走协调层，语音保持同一个 Agent 对接对象。
- [ ] **56：开发真机横屏验收即时工具与后台并行。** Worker 正在运行时询问时间、列工作目录、操作底座，再继续询问任务。完成标准：即时工具可响应，任务保持运行，随后结果经协调层回到语音。
