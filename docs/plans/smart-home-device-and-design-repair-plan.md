# 智能家居修复方案：真机能力、拖边布局与设计还原

## 1. 调研结论与依据

修复要同时打通设备能力链路和界面组合方式。仅增加风速按钮不能解决 MIoT 参数不可写、HA 参数被裁掉、能力未组装及详情页空白的问题。

2026-11-10 在魅族 20 Pro 真机上检查现有 Android 开发宿主，横屏分辨率为 2400×1080，屏幕密度为 440dpi。通过临时只读探针，使用手机当前米家账号读取 46 台设备的规格与属性，并读取当前应用组装出的 44 张设备卡片。没有发送家电控制命令。探针已撤除，原开发会话与跟随系统的外观设置已恢复。

## 3. 布局和交互决策

### 3.1 入口收敛

- 顶栏保留“我的设备 / 服务绑定”、刷新图标和返回；删除顶栏“调整布局”。刷新图标沿用现有 `ActionIcon refresh`，触控区域 44×44dp，读屏名称为“刷新设备”；手动刷新期间在原位置显示进度。
- 布局编辑作用于一个房间。单房间页的房间标题仅保留一个布局图标；全屋概览各房间标题各有一个同位置图标，明确对象。卡片长按也进入所属房间的编辑状态。
- 编辑状态仅在该房间标题显示“完成”，删除额外编辑横幅和卡片内的尺寸/移动按钮。设备详情页不显示布局入口。
- store 的全局 `homeLayoutEditing: boolean` 改为编辑房间 ID；由该身份决定把手和完成按钮，保证全屋概览也只有一个房间进入编辑。
- 全开/全关属于房间设备操作，放在房间标题的更多菜单内，菜单名称明确为“灯和插座全开/全关”，与现有实际执行范围一致。普通浏览时优先呈现房间名、环境和开启数量。

### 3.2 拖边调整大小

内部规格采用 `1x1 / 2x1 / 1x2 / 2x2`，去掉界面上的尺寸选项。新增 `1x2` 用于保证下边只改高度、右边只改宽度；其成本是扩充 span 枚举、解析和共享尺寸映射，并让内容组合支持窄高区域。相比强迫用户下拉时同时扩宽，这个小幅增加的几何状态更符合直接拖拽的预期，不增加新的存储实体或依赖。

1. 长按卡片或点房间布局图标进入编辑；选中卡片显示右边、下边和右下角的短把手。视觉把手细，实际触控范围为 44dp。
2. 右边控制宽度；下边控制高度；右下角同时控制两轴。拖动中显示轮廓预览和邻居让位，不写持久化。
3. 以当前画布测得的单元宽高和间隔计算吸附点；超过相邻规格中点后切换候选，边界增加 8dp 滞回，避免手指在边界附近反复跳格。
4. 从 `1x1` 下拉变为 `1x2`，右拉变为 `2x1`，角拖可到 `2x2`；`2x2` 收窄变为 `1x2`，收矮变为 `2x1`。落位与预览一致，两个轴独立。
5. 松手提交一次 span；手势取消恢复起始 span。保持原有 span/order 存储结构，读取时支持新增枚举，旧的三个值原样保留；重新打开仍呈现保存后的规格与顺序。
6. 卡片主体拖动负责房间内排序，边缘拖动负责缩放；编辑期间卡片电源、滑杆和动作不执行。正文区域仍可滚动，把手区域由手势接管。

使用项目已有的 `onLayout`、`pan`、`onPanStart/onPanEnd`、`panActivation` 和必要的触摸事件。以上接口已在当前 `.nsh/types/nsh/types.d.ts` 核对。参照当前 `SteplessWheel` 对滚动容器内手势的接管方式；参数滑杆继续复用基于 NSH `Slider` 的 `HorizontalValueSlider`，无需引入 Web 拖拽库。

布局草稿属于当前房间的编辑会话；原始设备状态继续轮询，不能覆盖手势草稿。卡片身份固定为设备 ID，状态和尺寸通过响应式绑定更新；删除目前把温度、开关等塞进 `applianceKey` 造成整卡重建的做法，否则拖动中的卡片会因轮询而重建。

### 3.3 画布几何

- 通过右侧画布 `onLayout` 获取实际可用宽度，按最小卡宽 208dp、间隔 12dp 计算列数：`floor((width + 12) / (208 + 12))`，至少一列。在本机当前宽度下应为两列。
- 卡片高度采用固定基础行高与行间距，`2x2` 高度严格等于两行加一个间距，避免 CSS 自动行高被大卡内容撑高后，小卡留下大片空白。
- 以 order 和 span 做稳定顺序排布；扩缩卡片时，后面的设备依原顺序流动。替换 `row dense` 越过前项回填空洞的规则，避免视觉顺序与保存顺序不同。
- 一列时显示宽度收缩，但保存的 span 不变；重新获得空间后恢复。复用 span/order，新增集中式尺寸映射，让 UI 和布局解析统一理解列跨度与行跨度，避免散落 `span !== 1x1` 这样的三规格假设；不增加任意坐标和断点独立布局。

## 4. 设计稿还原规格

设计基准同时使用房间分组图的信息层级和 Bento 图的尺寸展开方式。共用卡片和能力组件，普通设备收紧、复杂设备按内容展开。

| 部位 | 修复后的规则 |
| --- | --- |
| 房间 | 一个完整的视觉区域承载房间标题、环境和设备；房间间距大于卡片间距；开启数量退到右侧弱层级 |
| 普通卡片 | 图标、设备名/状态和电源构成固定对齐槽。名称允许两行；已有房间上下文时省略重复房间前缀，厂商长产品名用设备别名呈现；超出两行仍可省略，详情展示完整原名。`1x1` 不为不存在的控件留空 |
| PM2.5 | 叶片图标 + 数值 + 设备提供的质量等级；详情显示 `μg/m³`。真机净化器存在 `air-quality=0/Excellent`，可绑定为“优”；按同一物理设备配对数值和等级，不将 PM2.5 浓度直接当 AQI |
| 温湿度 | 温度计/水滴图标替代重复的“温度/湿度”文字；数值与单位紧凑排列，沿用中性表面 |
| 台灯 | 增加台灯轮廓，与吸顶灯区分；开启时灯罩和光晕呈暖色，关闭态为低强调灰；亮度、色温、模式按实际能力显示 |
| 风扇 | 有底座和扇叶的轮廓，开启态用冷蓝色；摘要可显示“1档 · 直吹风”，关闭时写“已关闭 · 记忆1档”，不把记忆档位当作正在送风 |
| 设备图标 | 保留 Canvas 矢量方案，统一 24 单位画布和光学中心；增加 lighting、airflow、air-quality 的语义 token（主题色变量），分别承担暖光、送风、空气等级含义；明暗主题均定义 |
| 图标状态 | 活跃图标用语义底色、前景和克制光晕；电源用明确开/关形态。避免当前“所有开启图标都变成纯黑/纯白方块” |
| 摘要 | 依据能力挑选 1～2 项主状态，例如“制冷 · 22.5°C”“强力 · 基站充电”；来源进入低强调副信息，型号放到详情 |
| 监控 | 有真实媒体会话才展示画面及流状态；未建立视频连接时呈现设备状态与连接入口；分辨率取媒体结果，存储按规格单位换算 |

大卡应增加有用内容，而不是放大空白。标题字号、卡片内边距和分割线用已有设计变量统一；避免在每个 renderer 内单独叠边框与胶囊。

`RoomEnvironmentMetric` 增加来源设备与指标实体身份，聚合时保留到房间层。房间有多个 PM2.5 来源时，按固定设备优先级选择有效来源，同时从该设备选择质量等级；该设备没有等级就只显示数值。不能把净化器的浓度与新风的等级拼成一个标签。窄高 `1x2` 仍使用同一组元语，主控纵向排列，不复制一套设备页面。

## 5. 通用能力与控件组装

### 5.1 选用现有实体链路，补足属性语义

继续使用 `HomeEntityDefinition → HomeStateSnapshot → HomeAppliance`。MIoT 属性映射为现有的 `switch/number/select/sensor/button` 实体；HA 保持其原生服务。将服务类型、属性名和稳定语义标识保留到归一化层，避免聚合器依赖设备显示名正则推断。

| 原始能力 | 归一化 | 表现元语 |
| --- | --- | --- |
| 可读写 bool，如摇头 | `switch`，绑定 `turn_on/turn_off` | Toggle（开关） |
| 数值 range，如空调温度 16～31、step=0.5 | `number`，保留 min/max/step/unit | Range（数值调节） |
| value-list，如风扇 1～4 档、三种风类 | `select`，保留原始值与本地化标签 | Choice（选项） |
| action，如清扫/回充 | `button` 或现有动作描述，保留输入参数定义 | Action（动作） |
| 只读状态，如温湿度、剩余时间、电量 | `sensor`，保留单位、枚举和来源 | Metric（指标） |

新增统一 `controls` 数组，放在现有 `ApplianceCapabilities` 内。每项是上述五种类型之一，携带稳定 key、语义、标签、当前值、可用状态，以及适用的范围/枚举/命令。可用状态区分读取失败、已知只读和可控制；未知值用空值表达，不转成关闭或零。命令复用当前 `entityId/domain/service/parameterKey` 结构；MIoT 的 did/siid/piid/aiid 保留在 transport 内部，UI 不拼原生请求。

这个数组解决一台设备同时存在多个模式、数值和开关的问题：当前单一 `modeBar` 装不下风类、档位和摇头角度。`power/dimmer/thermostat` 等已有结构先由同一份归一化数据派生，用于保持现有调用方；控件迁移完成后删除不再使用的兼容字段，避免长期维护两份状态。

### 5.2 四层职责

| 模块 | 负责内容 | 调用方得到什么 |
| --- | --- | --- |
| `home-assistant` 的 source adapters | 保留规格读写元数据；归一化原始值；构造实际服务调用；回读参数/动作结果 | 可读取、可执行的实体定义和快照 |
| `home-devices` | 按语义聚合同一物理设备，产生 controls、摘要、图标变体、房间环境；定义各尺寸内容优先级 | 与 MIoT/HA 无关的设备展示模型 |
| `HomeRuntime` / store | 连接、轮询、命令生命周期、设备当前值与操作中状态、布局持久化 | 当前 dashboard 和现有 control/layout 方法 |
| NSH 家居组件 | 渲染五类元语、卡片、专属媒体/周期区和手势 | 统一呈现和交互；不按型号构造命令 |

纯计算采用函数，例如 `buildControls(records)` 和 `selectCardContent(appliance, span)`；连接/请求仍由已有 runtime/transport 类维护。缩放编辑的 signal（响应式状态）随房间编辑会话创建和清理。这里的选择依据是状态生命周期，不建立每类家电的继承体系。

已有 `home-devices` package 继续承担可复用模型；NSH 控件放在 `apps/nsh/ui/home/`，因为它们依赖当前 NSH 主题、手势和组件系统。暂不增加 UI package、注册插件系统或第三方状态管理：当前只有一个界面调用方，增加包边界不会提供额外复用收益。

### 5.3 命令闭环必须补齐

1. MIoT：`parseMiotSpec` 保留 actions 及其输入参数引用；可写属性不再无差别降为只读。`DirectMiotTransportAdapter` 增加 `set_value/select_option`、辅控开关及动作调用；`MiotHttpClient` 增加与规格绑定的 action 请求。
2. HA：按实际 feature bits（功能位）产生调速/预设/摆风能力；属性白名单补齐 `percentage_step/preset_mode/oscillating/direction/fan_mode/swing_mode` 等当前值。`percentage=25`、step=25 对应这台风扇的一档，不能丢失步长后画出任意无级值。[HA 风扇实体规范](https://contributors.home-assistant.io/core/entities/fan/)
3. Gateway：加入实际需要的 `set_percentage/set_preset_mode/oscillate/set_fan_mode/set_swing_mode`，并定义各服务对应的回读字段；不能沿用“只检查 on/off”的完成条件。MIoT `select_option` 的选项 ID 与原始数值保持确定映射，界面翻译不进入命令匹配。
   - Action 单独定义规格输入、执行输出和关联状态判据。例如 `Start Sweep` 关联扫地机 s2/p1 的清扫状态，`Start Charge` 关联 s3/p2 充电状态及 s2/p1 回充状态；按设备实际状态机确定目标值。
   - 当前 `press` 仅比较 `last_updated`，MIoT 每次读取都会刷新该时间，不能用于确认动作。传输接收与状态确认分别表达；没有可观察完成状态的动作使用协议明确返回的结果，只能呈现其能证明的执行阶段，不能把一次重新读取认作动作完成。
4. 稳态数据只保存一份。拖动参数时控件显示本地预览，松手发送一次；现有开关即时反馈继续复用。设备回读、外部米家修改和轮询结果更新同一能力值，卡片与详情同步。
5. 原始未知字段保留在能力清单中；进入产品控件的字段必须有明确语义、类型和命令绑定。对于食谱 JSON、巡航字符串等复合数据，以已定义的专属编辑区呈现，不把原始协议字符串做成普通输入框。

### 5.4 风扇的端到端样例

| 真实字段 | 当前值 | 能力与命令 | 卡片/详情 |
| --- | --- | --- | --- |
| `fan on`，s2/p1 | false | power，`turn_on/turn_off` | 电源按钮 |
| `fan-level`，s2/p2 | 1；选项 1/2/3/4 | `fan.speed` Choice，`select_option` → 对应 MIoT 数值 | 小卡摘要；宽卡 4 档分段；详情完整可调 |
| `mode`，s2/p3 | 0；直吹/自然/睡眠 | `fan.mode` Choice | 宽卡/详情模式分段 |
| `horizontal-swing`，s2/p4 | false | `fan.oscillation` Toggle | 详情摇头开关 |
| `horizontal-swing-included-angle`，s2/p5 | 90；30/60/90/120/150 | `fan.swingAngle` Choice | 大卡/详情角度；摇头关闭时仍可设置记忆角度 |
| 指示灯 s4/p1、提示音 s5/p1、童锁 s7/p1 | false/true/false | settings Toggles | 详情“设备设置” |

调用方只需要把 `appliance.capabilities.controls` 交给统一控件组合，并将用户操作提交到 store 现有命令入口。首页与详情消费同一 control ID，不分别推导风速。HA 来源也使用 `fan.speed` 语义，但由自己的命令绑定调用 `fan.set_percentage`。

这台风扇规格明确是四档，不能套用其他型号的 1～100 无级风速。单步左转/右转为独立 action，读取能力时保留，后续验证动作语义后再加入方向控制。

## 6. 按真实设备组装，而不是填满所有元语

| 设备 | 小卡 | 宽卡/大卡 | 详情与需要补齐的字段 |
| --- | --- | --- | --- |
| 风扇 | 开关 + 档位/风类摘要 | 档位、风类；大卡增加摇头 | 角度、指示灯、提示音、童锁 |
| 空调 | 制冷/制热 + 设定温度 | 温度调节、模式、风速 | 16～31°C、0.5°C 步长；自动及 1～8 档、上下扫风/角度；辅热/ECO 等分组显示 |
| 卧室台灯 | 开关 + 亮度 | 亮度和 2600～5100K 色温 | 真实 11 项模式；超过分段容量使用 Select（选择器），不截掉后六项 |
| 大厅台灯 | 开关 + 亮度 | 亮度 | 模式规格是 0～3 数值范围，先保留原始值；明确模式含义后提供语义选项，不虚构色温 |
| 净化器/新风 | PM2.5 + 工作模式 | 模式、档位、温湿度 | 滤芯寿命/剩余时间、设备设置；指标与控制同时存在 |
| 扫地机 | 当前状态 + 电量 | 清扫/回充等主要动作、吸力模式 | 主/边刷、滤芯、拖布分别保留服务 ID；现有两组 brush 因同名被遗漏的问题需修正 |
| 洗衣机/洗碗机 | 各自的真实阶段和剩余时间 | 实际支持的启动/暂停/停止与程序 | 洗衣机温度/转速/漂洗次数；洗碗机洗涤程序/门状态/软水盐，分别组装 |
| 电饭煲 | 原始工作状态 | 程序与剩余时间在有对应字段时展示 | 规格 `Start Cook` 含输入参数；私有菜谱是复合数据，需要单独解析，删除无字段依据的“精煮饭”和阶段进度 |
| 摄像头 | 开关/休眠与状态摘要 | 有媒体会话后显示视频 | 夜视、录像模式、追踪、存储；P2P action 存在不代表已有解码播放能力，媒体会话需独立接入 |
| 喂食器/饮水机 | 当日统计和缺粮/缺水状态 | 出粮量/工作模式等主要操作 | 使用真实 action 输入与结果；按来源支持情况展示 |

一个尺寸放不下的内容进入详情，完整能力不因卡片缩小被删除。字段读取失败显示该项暂不可用；零值、关闭值和缺字段分别处理，不能补成“正常/待机/0分钟”。
