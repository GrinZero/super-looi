# Voice Agent 自然委派与温热上下文

用户交代一件事后，LOOI 立即自然承接，后续语音交流可以继续；完成结果在空闲时交回来。首页移除右下角停止任务按钮。后台 LLM 在持续交流中复用同一上下文，连续空闲 15 分钟后下一次请求开启新的上下文。

## 接口与职责

- `VoiceTaskBridge.submit(prompt)` 立即返回已受理及任务 ID；执行继续归现有 `VoiceTaskCoordinator`，结果通过 `onNotice` 回传。移除快路径窗口，所有委派只有一条结果回流路径。
- Store 保留 `busy` 的执行互斥用途，使用语音执行来源区分前台呈现。语音执行不改写首页进度与文字回复；交互问题和任务详情仍由现有入口维护。
- 温热上下文只管理后台逻辑 sessionId、活动时间和运行状态；调用方在开始执行时取得 ID、执行结束时刷新空闲起点、用户交流时续期。消息继续由 `SessionTranscriptStore` 保存和恢复。
- `VoiceRuntime` 保存待机期间到达的通知，并在下一次语音会话中交给现有空闲播报队列。

代表调用：语音工具提交 → 返回受理 → 用户继续交流；后台执行完成 → 回传结果 → 当前语音空闲时表达，或下次唤醒后表达。后台执行 sessionId 独立于前台文字 conversationId 和语音 WebSocket。

## 取舍

只隐藏按钮不能解决对话等待和全局状态耦合；直接清除 `busy` 则会改变单执行器的互斥行为。因此保留执行状态，只分离呈现。立即受理使短任务也经通知交付，代价是少了一次工具内直接返回，收益是取消按耗时分流与固定等待。

温热窗口复用已有消息存储，新增成本是一个小型会话生命周期模块与语音活动回调。采用惰性到期检查，不设置后台清理定时器；运行中及等待用户时不切换上下文。窗口是产品会话策略，不等同供应商连接、模型驻留或提示词缓存期限。

只读 shell 的两类查询需求已确认。本步以研究记录给出接入依据，直接只读执行工具随后单独实现；其接口需要同时覆盖文件／环境读取与已有 App 查询能力。
